What is OPC-UA?

OPC Unified Architecture is the de-facto standard for secure, reliable, platform-independent data exchange in industrial automation. It replaces the legacy COM/DCOM-based OPC Classic and adds a layered security model — but security is optional by configuration.

Three security modes can be set per endpoint session: None, Sign, and Sign & Encrypt — each with dramatically different attack surfaces.

OPC-UA 1.00 2006 · Foundational
First unified spec. Introduced binary UA-TCP transport and the core security framework. Many PLCs still ship with this version.
LEGACY
OPC-UA 1.03 2015 · Widely Deployed
Added HTTPS transport, PubSub precursor, improved certificate management. Most SCADA deployments in production today.
COMMON
OPC-UA 1.04 2017 · PubSub + GDS
Full PubSub model, Global Discovery Server (GDS), improved security policies. Recommended for new deployments.
RECOMMENDED
OPC-UA 1.05 2022 · Current
Reverse Connect, improved Role-Based Access Control (RBAC), enhanced PubSub security. Mandates TLS 1.2+ for HTTPS.

Attack Vectors
A
Vector 1 — Passive Sniffing
Attacker on same OT VLAN runs Wireshark/tcpdump targeting port 4840. OPC-UA UserNameIdentityToken sends credentials as plaintext in the ActivateSession request body. Credentials captured immediately.
B
Vector 2 — ARP Spoofing / MitM
Attacker poisons ARP cache to intercept traffic between OPC-UA client and server. Kills existing session via TCP RST, waits for automatic reconnect — client re-authenticates sending credentials through attacker's relay.
C
Vector 3 — Session Token Replay
Captured AuthenticationToken from a valid session can be replayed within the session timeout window. Attacker injects Write requests using the stolen token — no need to crack the password.
D
Vector 4 — Credential Brute Force
OPC-UA servers without lockout policies allow unlimited login attempts. Automated tools (e.g. opcua-client-cli) can brute force common OT default credentials.
MitM Kill Sequence — Step by Step

Why This Mode Blocks Attacks
✔
Mutual Certificate Authentication
Both client and server must present valid X.509 certificates. Server validates client cert against its trusted store — anonymous or username tokens are rejected at handshake.
✔
End-to-End Encryption (SignAndEncrypt)
Full message signing + AES-256 encryption. Passive sniffing yields only ciphertext. MitM cannot decrypt or modify payloads without the private key.
✔
Certificate Pinning Blocks MitM
OPC-UA servers maintain a certificate trust list. A rogue certificate (attacker proxy) is rejected — the ARP-spoof relay technique fails as the handshake aborts.
✔
Residual Risk — Endpoint Compromise
Attack surface shifts to key theft or endpoint compromise: stealing the private key from the client/server filesystem, or compromising the HMI that holds a trusted certificate.
Secure Configuration Checklist
✔
Disable SecurityMode = None endpoints
Remove anonymous + unauthenticated endpoints from server configuration
✔
Use SignAndEncrypt mode only
Policy: Basic256Sha256 or Aes256Sha256RsaPss (avoid Basic128Rsa15)
✔
Issue device-specific certificates
Each OPC-UA client gets a unique cert — enables per-device revocation
✔
Implement Role-Based Access Control
OPC-UA 1.04+ RBAC — restrict Write/Call permissions per identity
✔
Monitor certificate expirations via GDS
Use Global Discovery Server for automated cert lifecycle management

Key Takeaway:
OPC-UA security is opt-in. A server configured with SecurityMode=None gives any network-local attacker full industrial process control with zero effort. Username/Password adds a credential barrier that collapses under passive sniffing. Only SignAndEncrypt + Certificate eliminates network-layer attack vectors.
🔓 MODE 1 → NEVER DEPLOY 🔑 MODE 2 → LEGACY ONLY 🛡️ MODE 3 → REQUIRED
